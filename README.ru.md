## Обзор

TCP-пакеты передаются через Transport. На данный момент доступны три транспорта:
1. Yandex (`--transport yandex`) — отправляет пакеты через курсорные сообщения Yandex Docs, **старый** редактор документов;
2. Volga (`--transport vyandex`) — то же самое для **нового** редактора, пакеты идут через Volga session API. Выбирайте его для документов, которые открываются в новом редакторе. Работают ссылки и `disk.yandex.ru`, и `disk.yandex.com`: сессия привязывается к тому хосту, которому принадлежит документ;
3. Max (`--transport oneme`) — отправляет пакеты через WebRTC DataChannel.
   - **Не использовать** основной или важный MAX-аккаунт.
   - **Не использовать** аккаунт, удаление или потеря доступа к которому критичны.
   - Использование через **внешний VPS** может привести к **ограничению аккаунта**.
   - **Ограничение может сохраняться** после остановки OpenFlux.
   - MAX transport следует считать **экспериментальным** до выяснения механизма блокировки.


Клиентская часть запускает SOCKS5-прокси, выходная нода декапсулирует и пересылает пакеты в пункт назначения.

## Использование

### 1. Настройка выходной ноды
1. У вас должен быть root-доступ выходной ноде;
2. Поддерживается только устаревший редактор документов Yandex (переключается в настройках интерфейса).

TCP-соединения выходной ноды живут в userspace-стеке (gvisor), у ядра нет для
них сокета, и оно слало бы RST на каждый ответный пакет — туннель бы рвался.
Этот RST надо подавить, но **точечно**, не на весь хост. Глухое
`-j DROP` на все исходящие RST превращает закрытые порты в «молчащие»
(сканер видит `filtered` вместо `closed`) и мешает хосту нормально сбрасывать
посторонние соединения.

Рекомендуется (сужение по выделенному egress-IP):
```bash
# повесьте на машину второй/алиас IP под туннель, напр. 203.0.113.10
sudo iptables -A OUTPUT -p tcp --tcp-flags RST RST -s 203.0.113.10 -j DROP
sudo ./universal-bypass-tool --exit-node --local-ip 203.0.113.10 \
    --url "YOUR_YANDEX_DOC_URL" --debug
```
Ещё чище — запускать ноду в отдельном network namespace / контейнере, тогда
правило вообще не трогает сервисы хоста. `-m owner --uid-owner` тут **не
работает**: рвущие туннель RST генерит ядро без сокета-владельца, и owner-матч
не срабатывает.

Запасной вариант на весь хост (только на однозадачной машине, с пониманием
последствий):
```bash
sudo iptables -A OUTPUT -p tcp --tcp-flags RST RST -j DROP
sudo ./universal-bypass-tool --exit-node --url "YOUR_YANDEX_DOC_URL" --debug
```

### 1. Настройка десктопного клиента:

Команды для настройки десктопного клиента:
```bash
./universal-bypass-tool --client --url "YOUR_YANDEX_DOC_URL" --socks5 :1080 --debug
```

Затем настройте SOCKS5-прокси в браузере на localhost:1080.

## Шифрование

> **Совместимо со старыми пирами.** Keep-alive теперь проходит через то же
> сжатие и шифрование, что и обычный трафик, а не является постоянным
> маркером в открытом виде, при этом реальные пакеты передаются байт в байт.
> Клиент и выходная нода на разных сборках по-прежнему понимают друг друга,
> так что обновлять можно по одной стороне. Для включения шифрования, разумеется,
> нужны обе.

Сам транспорт передаёт пакеты как base64 внутри сообщений документа. Хопы до
провайдера идут по TLS, поэтому провайдер связи и локальная сеть не видят
ничего — но TLS терминируется у провайдера документа, а сам документ является
точкой встречи. Без слоя ниже **провайдер документа видит каждый пакет
туннеля в открытом виде**, а любой, у кого есть URL документа, может и читать
туннель, и внедрять в него свои пакеты.

Включите сквозное шифрование AES-256-GCM, добавив общий секрет в URL:

```
ydocs://DOC_URL#SHARED_SECRET
```

Обеим сторонам нужна **одна и та же ссылка**. Всё до последнего `#` — это URL
документа (`https://` подразумевается), всё после — секрет, который никогда не
покидает машину и служит только входом для деривации ключа.

```bash
# выходная нода
sudo ./universal-bypass-tool --exit-node \
    --url "ydocs://docs.yandex.ru/docs/view?id=YOUR_DOC#a-long-shared-secret" --debug

# клиент
./universal-bypass-tool --client \
    --url "ydocs://docs.yandex.ru/docs/view?id=YOUR_DOC#a-long-shared-secret" \
    --socks5 :1080 --debug
```

При старте обе стороны пишут в лог `Transport encryption: AES-256-GCM enabled`.
Клиенты iOS и Android принимают такую же ссылку в поле URL.

Подробности:

- Секрет должен быть не короче 16 символов. Сгенерировать:
  `openssl rand -base64 32`.
- У каждого направления свой производный ключ, каждый пакет несёт случайный
  nonce, повторы отбрасываются в пределах ограниченного окна.
- Обычный `https://` URL сохраняет прежнее поведение без шифрования.
- Чтобы секрет не попадал в историю шелла и вывод `ps`, передайте обычный URL
  вместе с `--encryption-key-file /path/to/secret`. Формы совместимы: пир с
  файлом ключа и пир со ссылкой `ydocs://` получат одинаковые ключи, если
  совпадают URL документа и секрет.

## Несколько выходных нод на одном VPS

По одной выходной ноде на ссылку. Они уживаются на одном IP, но несколько
деталей определяют, будет это работать хорошо или плохо.

Заведите на каждую ссылку свой systemd-инстанс со своим env-файлом:

```ini
# /etc/systemd/system/openflux-exit@.service
[Unit]
Description=OpenFlux exit node (%i)
Wants=network-online.target
After=network-online.target openflux-rst-drop.service
Requires=openflux-rst-drop.service

[Service]
Type=simple
EnvironmentFile=/etc/openflux/instances/%i.env
ExecStart=/usr/local/bin/openflux --exit-node --transport ${TRANSPORT} --url ${YANDEX_DOC_URL} $EXTRA_ARGS
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```sh
# /etc/openflux/instances/phone.env
TRANSPORT=vyandex
YANDEX_DOC_URL=https://disk.yandex.com/i/YOUR_DOC
EXTRA_ARGS=
```

```bash
sudo systemctl enable --now openflux-exit@phone.service
```

`TRANSPORT` берётся из файла инстанса, а не из юнита, поэтому разные ссылки
могут использовать разные транспорты на одной машине.

### Следите за счётчиком потерь raw-сокета

Каждая выходная нода открывает raw TCP-сокет, и **каждый** raw TCP-сокет на
хосте получает копию **каждого** TCP-пакета — туннелей соседних инстансов,
SSH, всего остального. Инстанс отбрасывает чужое, но чтобы это понять, пакет
нужно прочитать. Если инстанс не успевает разгребать сокет, ядро молча
выбрасывает лишнее: ни ошибки, ни лога, просто необъяснимые потери внутри
туннеля.

Этот счётчик — первое, что нужно смотреть, когда несколько ссылок «работают
плохо»:

```bash
grep ":0006" /proc/net/raw | awk '{print "drops=" $NF}'
```

По строке на каждую выходную ноду, последняя колонка — накопленное число
потерь. Оно должно оставаться нулевым или близким к нулю. Если растёт —
ноды не справляются.

Этому помогают два изменения:

- Egress-IP определяется один раз, а не на каждый пакет. Раньше он
  вычислялся заново для каждого пакета в обе стороны, а определение открывает
  и закрывает UDP-сокет, так что стоимость росла и с трафиком, и с числом
  инстансов.
- Буфер приёма raw-сокета поднят до 8 МБ против 208 КБ по умолчанию, чтобы
  переживать всплески.

Если потери всё равно растут, у машины просто нет запаса: держите меньше
инстансов на хост или выдайте каждому отдельный egress-IP через `--local-ip`,
чтобы ядро давало ему меньше лишнего.

### Размер пула релея

Пул релея `vyandex` рассчитывается от числа ядер (128 воркеров на ядро,
максимум 1024). Раньше это были фиксированные 2000 воркеров и место под 2000
простаивающих TLS-соединений на инстанс — столько туннелю не нужно: в батче до
20 пакетов, так что даже нагруженная ссылка держит в полёте лишь десятки
запросов. На одноядерном VPS с тремя выходными нодами это выливалось в тысячи
горутин, дерущихся за одно ядро.

Переопределить можно так:

```sh
# /etc/openflux/instances/phone.env
OPENFLUX_RELAY_WORKERS=256
```

## Пропускная способность

Передача через сервис документов — это путь с большой задержкой: около 190 мс
на круг на тестовом VPS против 45 мс напрямую. Именно задержка определяет
скорость, потому что TCP-соединение держит в полёте не больше одного окна
данных за круг.

Отсюда две настройки, обе в `tunnel/tunnel.go`:

- **CUBIC вместо Reno.** `tcp.NewProtocol` в gvisor до сих пор по умолчанию
  использует Reno: окно растёт линейно и вдвое срезается на каждой потере. На
  пути в 190 мс это восстанавливается слишком долго. `tcp.NewProtocolCUBIC` —
  тот же стек с алгоритмом, рассчитанным ровно на такой случай.
- **Окна под круговую задержку.** Буферы приёма и передачи ограничивают окно,
  а окно за круг ограничивает скорость. Прежние 256 КБ по умолчанию упирали
  одно соединение примерно в 1,3 МБ/с независимо от доступной полосы. Это
  лимиты, а не резервирование, поэтому простаивающие соединения ничего не
  стоят.

Замеры на тестовом VPS, загрузка через одну выходную ноду:

| | было | стало |
|---|---|---|
| один поток 8 МБ | 66,4 с (120 КБ/с) | **6,6 с (1,22 МБ/с)** |
| 16 МБ в 4 потока | не уложились в 150 с | **12 с** |

Третья настройка — сборщик мусора выходной ноды. Раньше он был жёстко задан
как `GOGC=20`, и на одном ядре это отнимает реальное время пересылки на уборку
после JSON, base64 и TLS каждого батча. Замеры на той же загрузке 8 МБ:

| GOGC | скорость | память |
|---|---|---|
| 20 (было) | 1,10 / 0,98 МБ/с | 46 МБ |
| 100 (теперь по умолчанию) | **1,23 / 1,11 МБ/с** | 72 МБ |
| 400 | 1,09 / 1,08 МБ/с | 211 МБ |

Больше — не значит лучше: крупная куча обходится дороже, чем экономит. `GOGC`
и `GOMEMLIMIT` из окружения имеют приоритет, причём `GOMEMLIMIT` — более
удачный рычаг на действительно тесной по памяти машине, так как ограничивает
кучу, не заставляя собирать мусор на каждом мелком приросте.

Круговая задержка не изменилась — около 0,76 с на маленький запрос. Это сам
релей, локальными настройками её не убрать, поэтому туннель всегда будет
ощущаться медленнее своего канала, даже когда объёмы качаются быстро.

Буферы намеренно не применяются к iOS Network Extension: она живёт под лимитом
около 50 МБ и пересылает сырые L3-пакеты без собственного стека.
